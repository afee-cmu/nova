# nova

BonApp helps small restaurants schedule the right people at the right time for the right tasks.

Built for the CMU ScottyLabs Nova x DoorDash hackathon, pain point 05 (staffing and skill optimization), BonApp turns a restaurant's roster, task skills, availability, and rush demand into a weekly staffing plan. It helps managers see coverage gaps and review changes when an employee calls out.

## How it works

```text
Data In (.xlsx) -> Standardize (code) -> Solve (OR-Tools) -> Explain (code templates)
                                         ^                         |
                                         +--- re-optimize (code) <-+ call-out

Natural-language update -> LLM interpretation, or keyword fallback -> code validates and applies rules
```

The workbook loader validates and converts workbook data; the solver computes assignments and gaps. In the web UI, an LLM may interpret a manager's update and phrase a response. Code and the solver compute schedules and enforce constraints and approval rules; the LLM does not decide premium-pay approval. The separate CLI pipeline also uses an LLM to extract setup and availability from text files.

## Quick start

Requires Python 3 and the packages below. From the repository root:

```bash
python -m pip install fastapi uvicorn requests openpyxl ortools python-multipart pandas
```

Set the OpenRouter key in the same terminal to enable AI interpretation in the web UI. Keep it in the environment; never commit it.

```bash
export api_key="your-openrouter-api-key"
uvicorn ui.server:app --reload
```

Open <http://127.0.0.1:8000>. Without `api_key`, the UI runs in offline mode: manager updates use the keyword parser, while schedule explanations use code-generated templates. The real workbook solver is still used when OR-Tools is installed; startup falls back to mock data if demo loading or solving fails.

Run the test files from the repository root:

```bash
python3 -m unittest test_schedule_input -v
python3 -m unittest test_reoptimize -v
python3 -m unittest test_security -v
```

The scheduler tests need OR-Tools; `test_schedule_input` skips its solver integration test if scheduler import fails. These tests are local and do not require a live OpenRouter request.

## Core modules

### Workbook input

[`schedule_input_template.xlsx`](schedule_input_template.xlsx) is the canonical workbook. `schedule_input.py` loads and validates its Roles, Tasks, Employees, Availability, Proficiency, RushWindows, and Policy tabs, then `to_scheduler_inputs()` maps task eligibility, availability windows, and wage data into the scheduler format. A person's Proficiency rows determine task eligibility; the proficiency score is recorded but is not currently used to rank assignments.

### Scheduler and pipeline

[`scheduler.py`](scheduler.py) expands rush profiles into shifts and demand, validates inputs, and uses Google OR-Tools CP-SAT to assign eligible, available employees subject to hour and shift caps. It reports uncovered demand as gaps and can export an Excel schedule. [`pipeline.py`](pipeline.py) is a separate CLI flow: it uses OpenRouter to extract setup and availability from text, validates the results, offers a manager review/correction loop, invokes the scheduler, and produces a report.

### Re-optimization

[`reoptimize.py`](reoptimize.py) re-solves after cancellations or emergency demand while rewarding retention of valid existing assignments. It returns a schedule diff, gaps, worker-rights flags, and problems. It makes no LLM or network calls; its output can vary between equivalent solver solutions.

### Security

[`SECURITY.md`](SECURITY.md) records the current code review and a checklist for deploying a web/API service. [`test_security.py`](test_security.py) checks for secret literals and dangerous sinks, verifies ignore rules, exercises workbook preflight and export sanitization, and checks file permissions. The checklist calls out web-service needs such as authentication, authorization, tenant isolation, and rate limiting.

## Web UI

### Goal and architecture

The UI is a thin web layer around the workbook loader and existing solver. Teammate modules remain outside `/ui`; the UI-specific backend, adapters, demo workbook, and static files live under `/ui`. It is a FastAPI backend with one vanilla HTML/JavaScript page and Tailwind loaded from a CDN; there is no npm or build step. Current schedules, explanations, employees, solver inputs, and pending approvals are kept in server memory, so state is reset when the process restarts.

`ui/solver_bridge.py` calls `load_workbook_input()`, `to_scheduler_inputs()`, `run_pipeline()`, and `reoptimize()`, then normalizes solver output for the page. It caches the demo solve and its original scheduler inputs at startup, and falls back to mock data if demo loading or solving fails. `ui/adapters.py` holds mock scheduling functions and keyword parsing; `ui/llm.py` handles update interpretation with validated JSON and a keyword fallback. To adapt a new solver result, update the bridge's `normalize()` and explanation builder while keeping the UI contract below; to change offline message parsing, update the adapter.

### Data In and workbook upload

The first screen lets a manager select or drop one `.xlsx` workbook (maximum 5 MB), download the canonical template, generate a schedule, or load the demo. The backend validates the workbook before solving. Validation errors are returned individually and leave the current schedule unchanged; warnings are shown on the schedule screen. Uploads are processed through a temporary file, then removed. The demo workbook is `ui/demo_data/demo_input.xlsx`.

### Schedule, stats, and employee details

The weekly grid shows each rush window under its day, with the time range, employee chips colored by task, and dashed gap indicators. The legend comes from the schedule's task list. Three stat cards show labor cost, coverage rate, and number of gaps. Selecting an employee opens a drawer with eligible tasks and rates, scheduled hours against the maximum (and minimum where present), and their assigned windows. Solver warnings can be expanded above the grid. `no_solution` and `invalid_input` show an error in place of the grid.

### BonApp Insights

The Insights panel shows a code-generated summary and one card per gap with explanation, suggested candidates/actions, and any manager-approval indication. Hovering a card or gap links the two; gap cards can be dismissed and restored. Copy summary copies the summary, gap titles, and suggested actions. Apply fix only sends an update when a named employee appears in its suggested action; otherwise it asks the manager to pick someone.

### Updates and approvals

The bottom update bar provides examples and accepts questions, call-outs, and coverage requests. With `api_key`, the backend asks OpenRouter's `openai/gpt-4o-mini` to interpret the message; it validates the response and retries once, then falls back to keyword parsing on invalid output, API failure, timeout, or missing key. Replies show the interpreted action and whether the source was AI or keyword. Questions use schedule data and do not change it.

For a call-out, the UI removes the employee's affected assignment(s) immediately and, when saved real solver inputs are available, presents a re-optimization proposal separately for manager approval. The proposal shows added/removed assignments and solver flags. Approving applies the stored proposal without another solve; rejecting keeps the schedule with the uncovered shift. If re-optimization is unavailable, the call-out removal remains and the UI reports the uncovered shift.

A cover that exceeds the employee's maximum hours, the 40-hour threshold, the workbook overtime threshold, or a less-than-11-hour turnaround is held for manager approval. These checks are performed in backend code. Approve applies the cover; reject discards it. **Reset demo** restores the schedule cached at startup and clears pending approvals. **Data In** returns to the upload screen. Status badges identify Real solver, Mock data, or Uploaded data, and AI mode or Offline mode (keyword).

### API reference

| Method | Path | Purpose and request | Response |
|---|---|---|---|
| `GET` | `/` | Serve the single-page UI. | HTML page. |
| `GET` | `/api/health` | Check backend and AI-key availability. | `status`, `mock_mode`, `ai_available`. |
| `GET` | `/api/schedule` | Read current in-memory state. | `schedule`, `explanation`, `employees`. |
| `GET` | `/api/template` | Download the canonical workbook template. | `.xlsx` file. |
| `POST` | `/api/upload` | Multipart form with one `file` `.xlsx` workbook. | On success: `ok`, schedule data, warnings, `solve_seconds`; on validation failure: HTTP 422 with `errors` and `warnings`. |
| `POST` | `/api/update` | JSON body `{"message":"..."}`. | Reply, parsed action/source, optional change/approval details, current schedule data. |
| `POST` | `/api/approve` | JSON body `{"change_id":"...","approve":true}`. | Reply, optional change, and current schedule data. |
| `POST` | `/api/reset` | Restore startup demo cache and clear pending changes. | Current schedule data. |

### UI schedule data

The normalized schedule contains status and source plus `windows`, `tasks`, `assignments`, `demand`, `gaps`, `employees`, `labor_cost`, `coverage_rate`, and `warnings`. Each assignment identifies an employee, window, task, time, hours, wage, and cost; demand records needed, assigned, and missing headcount; gaps identify the shortfall for a window and task. For example:

```json
{"status":"optimal","data_source":"solver","windows":[{"key":"Fri_Dinner Rush","day":"Fri","name":"Dinner Rush","start":"17:00","end":"21:00"}],"tasks":["Grill"],"assignments":[{"employee_id":"E101","name":"Maria Alvarez","window_key":"Fri_Dinner Rush","day":"Fri","window":"Dinner Rush","start":"17:00","end":"21:00","task":"Grill","hours":4,"wage":19,"cost":76}],"demand":[{"window_key":"Fri_Dinner Rush","task":"Grill","needed":1,"assigned":1,"missing":0}],"gaps":[],"employees":[],"labor_cost":76,"coverage_rate":1,"warnings":[]}
```

`explanation` is `{ "summary": "...", "gap_explanations": [{"gap_id":"...","explanation":"...","suggested_action":"...","needs_manager_approval":false}] }`. The page also receives the employee list at the top level of the schedule API response.

### Safety, extension points, and limitations

The OpenRouter key is read from the backend environment and is never sent to the browser. LLM output is parsed and checked against the current roster, windows, tasks, and allowed action types; it is retried once and then falls back to keywords. Premium-pay, maximum-hours, and turnaround decisions are made in code. Solver outputs are not guaranteed deterministic, so the demo solve is cached at startup and Reset restores that cache; re-plan proposals are stored and applied only after approval without re-solving.

To add an example, adjust the example-chip logic in `ui/static/index.html`; examples are also derived from the current roster and gaps. To connect another solver output, adapt it in `ui/solver_bridge.py` and preserve the normalized fields. The UI is currently single-process and in-memory, with no authentication or tenant isolation; uploaded data and schedule state are not persistent across restarts. The proficiency score is not used for ranking, and the code does not implement demand forecasting or fairness scoring.

## Demo guide

1. Start the app and choose **Use demo data**.
2. Send **Maria Alvarez called out Friday Dinner Rush** (or choose a call-out example generated from the loaded schedule).
3. Review the proposed re-plan card and its assignment changes and flags.
4. Choose **Approve** to apply the stored proposal, or **Reject** to keep the uncovered schedule; use **Reset demo** to restore the cached original.
5. Try **Maria Alvarez will cover Sat Dinner Rush Grill** to see the code's hours/turnaround approval check when the current demo schedule and gap permit it. If that combination is not eligible in the current solve, use a suggested candidate for an open gap; the banner appears only when a rule check requires approval.

The demo roster includes Maria Alvarez, Leo Martinez, Jake Thompson, Lily Chen, and Sam Rivera; its rush windows are Lunch Rush and Dinner Rush. Solver assignments and resulting actions depend on the schedule computed at startup.

## Limitations and next steps

The UI keeps state in process memory and has no authentication or tenant separation. Proficiency scores do not yet affect assignment ranking. Demand forecasting and fairness scoring are not implemented.
