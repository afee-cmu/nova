# BonApp web UI

For the project overview, see the [repository README](../README.md). This guide covers only the web UI.

## 1. What this is

BonApp is a thin web layer around the existing workbook loader and weekly scheduler. It accepts the canonical `.xlsx` workbook, displays the resulting schedule and coverage gaps, and lets a manager review updates and call-out re-plans. Teammate modules at the repository root are imported without modification; UI-specific backend, browser code, adapters, and demo data live in `/ui`.

## 2. Quick start

From the repository root, install the packages used by the UI and its solver path:

```bash
python -m pip install fastapi uvicorn requests openpyxl ortools python-multipart
```

Set the OpenRouter key in the same terminal before starting Uvicorn to enable AI message interpretation. The key is read from the `api_key` environment variable; do not put it in source code or commit it.

```bash
export api_key="your-openrouter-api-key"
uvicorn ui.server:app --reload
```

Open <http://127.0.0.1:8000>. To run offline, omit the `export` command and start Uvicorn as above. The UI then uses keyword parsing for manager updates. Explanations are generated by code templates in either mode; the workbook solver does not require the key.

### If something goes wrong

- **Port already in use:** stop the other process listening on port 8000, or start Uvicorn on another unused port.
- **Missing module:** install the packages in the command above with the same Python environment used to run Uvicorn. Uploads also require `python-multipart`; the real solver requires `ortools`.
- **Page appears stuck on “Loading”:** this version should open on the Data In screen; it does not load a schedule on page load. Confirm you started `ui.server:app` from the repository root, then check `/api/health`. The schedule view appears after **Use demo data** or a successful upload.

## 3. What you can do

### Data In and workbook upload

Choose or drop a single `.xlsx` file up to 5 MB, download the canonical template, generate a schedule, or load the cached demo schedule. Invalid workbooks return validation errors in a red card and leave the current schedule unchanged. Loader warnings appear in a collapsible list on the schedule view. Uploads are written to a temporary file and removed after processing.

### Weekly schedule grid

The grid has one column per day and stacks that day's rush windows as cards. Each card shows the window name and time range, assigned employees as task-colored chips, and any open demand as a dashed gap chip. The task legend is built from the loaded schedule. Days without windows show “No rush windows.”

### Stats and status badges

The stat cards show labor cost, coverage rate, and gap count. Header badges show the solver status; data source (`Real solver`, `Mock data`, or `Uploaded data`); and AI availability (`AI mode` or `Offline mode (keyword)`). The health badge reflects whether `api_key` is set, not whether the OpenRouter service is reachable.

### Employee drawer

Click an employee chip to see that employee's eligible tasks and rates, scheduled hours against `max_hours`, `min_hours` when present, and assigned windows. The hours bar changes to orange above 90% of the maximum.

### BonApp Insights

The panel shows a code-generated schedule summary and one card per gap, with the shortfall, candidate suggestions, and an approval indicator where applicable. Hovering a gap or card highlights its counterpart. Cards can be dismissed and restored; **Copy summary** copies the summary, gap titles, and suggested actions. **Apply fix** sends a coverage update only when a suggested action names an employee; otherwise it asks the manager to choose someone and focuses the update input.

### Natural-language updates

The fixed update bar includes example messages derived from the current schedule, chat bubbles, and a loading indicator. With `api_key`, `ui/llm.py` asks OpenRouter's `openai/gpt-4o-mini` to interpret the message and produce a short reply. The UI shows an “Understood as” chip for interpreted call-outs and covers, plus an AI or Keyword source label. If there is no key, or the API call or response validation fails, the UI falls back to keyword parsing. Questions do not change the schedule and are answered from the schedule data sent to the model.

### Call-out re-plan

A recognized call-out removes the matching assignment(s) first. When saved solver inputs are available, the backend also asks `reoptimize()` for a proposal based on the original schedule and presents a separate card with added/removed assignments and solver flags. **Approve** applies the stored proposal; **Reject** leaves the schedule after the call-out removal. A proposal is not re-solved when approved. If re-optimization is unavailable or returns an unusable status, the removed assignment stays out and the UI reports that the shift is uncovered.

### Manager approval for a cover

A cover that would exceed an employee's `max_hours`, exceed 40 hours, exceed the workbook's `overtime_threshold_hours`, or leave less than 11 hours between consecutive-day assignments is held in an approval banner. These checks are performed in `server.py`. The pending cover is applied only after approval; rejecting it leaves the schedule unchanged. The threshold field is used by the UI's check as reference data; it does not authorize automatic overtime in the solver.

### Reset demo

**Reset demo** calls `POST /api/reset`, clears pending changes, and restores the schedule, explanation, employee list, and solver context cached at server startup. The same action is available as **Use demo data** on the Data In screen. It does not re-run the solver.

## 4. How it connects to teammate code

| UI step | Teammate function or file | Where called in `/ui` | What we pass in | What we use from the result |
|---|---|---|---|---|
| Read/validate workbook | `schedule_input.load_workbook_input(path)` | `solver_bridge.load_workbook_input()` | Uploaded temp workbook or `demo_input.xlsx` path | Normalized workbook data and `issues.errors` / `issues.warnings`; errors stop processing. |
| Convert workbook schema | `schedule_input.to_scheduler_inputs(data)` | `solver_bridge.load_workbook_input()` | Loader's normalized workbook dictionary | Scheduler `employees` and `config`. The exact pair is retained for later re-optimization. |
| Expand rush windows | `scheduler.build_shifts(config["rush_profile"])` | `solver_bridge.load_workbook_input()` | Per-day rush profile | Window metadata and per-window/task needed counts. |
| Solve schedule | `scheduler.run_pipeline(employees, config, xlsx_path=None, summary=None)` | `solver_bridge.solve()` | Scheduler employee list and config | Status, assignments, gaps, per-employee summaries, labor cost, warnings/errors. No export is requested. |
| Suggest people for gaps | `pipeline.gap_candidates(result, employees, shifts, limit=3)` | `solver_bridge.build_explanation()` | Current assignments, employee usage, gaps, exact scheduler employee data, and shift metadata | Up to three candidates per gap and their code-computed reasons. If this helper fails, the bridge uses a simple roster-based suggestion. |
| Interpret manager update | `ui.llm.parse_message()`; offline parser `ui.adapters.parse_update()` | `server.update()` via `llm.py` | Message, current employees, and normalized schedule | Validated action fields and short reply, plus `ai` or `keyword` source. |
| Re-plan a call-out | `reoptimize.reoptimize(employees, config, current_assignments, cancel=..., time_limit_s=5)` | `solver_bridge.propose_replan()` | Retained scheduler inputs, original V2 assignments, and cancellation scope | New normalized proposal, diff (`kept`, `added`, `removed`), flags, problems, and solve time. It remains pending until approval. |

The UI contract relies on the solver's fields `status`, `assignments`, `gaps`, `employees`, `labor_cost`, and `warnings` / `errors`; assignment and gap rows rely on employee IDs/names, shift keys, roles, hours, wage/cost, and missing counts. The workbook adapter relies on the loader's normalized keys such as `tasks`, `employees`, `task_skills`, `demand`, and per-employee availability. If a teammate changes those names or meanings, update the translation in `solver_bridge.normalize()` (and its input preparation) rather than changing the browser to match solver internals.

The UI does not call the text-extraction `pipeline.main()` flow. It calls `scheduler.run_pipeline()` directly for `.xlsx` input. `pipeline.py` is imported only for the code-generated `gap_candidates()` helper. The `standardize()`, `build_schedule()`, and `explain()` functions in `ui/adapters.py` are legacy mock hooks; the current real workbook path uses `solver_bridge.py` instead.

## 5. Architecture and files

```text
Browser (static/index.html)
        | HTTP / JSON and multipart workbook
        v
FastAPI (server.py) ---- in-memory schedule, explanation, employees, pending changes
        |
        +--> solver_bridge.py --> schedule_input.py --> scheduler.py
        |                             |                   |
        |                             +--> pipeline.gap_candidates()
        |                                                 +--> reoptimize.py (call-outs)
        +--> llm.py --> OpenRouter (optional)
                    \-> adapters.py keyword fallback

Startup: load demo_input.xlsx -> solve once -> normalize/cache; on failure use mock data.
```

| File or folder | Purpose |
|---|---|
| `ui/__init__.py` | Marks `ui` as a Python package for `uvicorn ui.server:app`. |
| `ui/server.py` | FastAPI routes, in-memory state, upload handling, updates, and approvals. |
| `ui/solver_bridge.py` | Loads workbook inputs, calls the solver, normalizes results, builds explanations, and proposes re-plans. |
| `ui/adapters.py` | Legacy mock adapter functions and keyword update parser. |
| `ui/llm.py` | Optional OpenRouter update parsing, JSON validation/retry, and keyword fallback. |
| `ui/mock_data.py` | Mock roster, schedule, and explanation used when real demo initialization fails. |
| `ui/static/index.html` | Single-page vanilla HTML/JavaScript UI; Tailwind is loaded from its CDN. |
| `ui/demo_data/demo_input.xlsx` | Populated demo workbook, copied from the canonical workbook template. |
| `ui/demo_data/make_demo_workbook.py` | Regenerates the demo workbook and can run a validation/solve report. |
| `ui/README.md` | This teammate-facing UI guide. |

There is no browser-side Python or npm build. State is process-local and in memory; run one server process for a consistent demo session.

## 6. API reference

| Method | Path | Purpose | Request body | Response summary |
|---|---|---|---|---|
| `GET` | `/` | Serve the UI page. | None | `index.html`. |
| `GET` | `/api/health` | Report service and key presence. | None | `status`, `mock_mode`, `ai_available`. |
| `GET` | `/api/schedule` | Return current UI data. | None | `schedule`, `explanation`, `employees`. |
| `GET` | `/api/template` | Download canonical workbook. | None | `.xlsx` file. |
| `POST` | `/api/upload` | Validate and solve an upload. | Multipart form field `file`; one `.xlsx`, at most 5 MB. | Success: `ok`, `schedule`, `explanation`, `employees`, `warnings`, `solve_seconds`. | `POST` | `/api/update` | Interpret and process an update. | JSON `{"message":"..."}` | `reply`, `change`, approval fields, `schedule`, `explanation`, `employees`, parsed action, and `source`. |
| `POST` | `/api/approve` | Apply or discard a pending cover or re-plan. | JSON `{"change_id":"...","approve":true}` | `reply`, optional `change`, and current schedule data. |
| `POST` | `/api/reset` | Restore startup demo cache. | None | Current `schedule`, `explanation`, and `employees`. |

## 7. Data contract

`GET /api/schedule` returns a `schedule` object with `status`, `data_source`, `windows`, `tasks`, `assignments`, `demand`, `gaps`, `employees`, `labor_cost`, `coverage_rate`, and `warnings`. The following shortened example is produced by `normalize_mock()` in `solver_bridge.py` (the full schedule has all windows and roster entries):

```json
{"status":"optimal","data_source":"mock","tasks":["Cashier","Fry","Grill","Pack","Prep"],"labor_cost":2597.5,"coverage_rate":0.90625,"warnings":[],"windows":[{"key":"Mon_Lunch","day":"Mon","name":"Lunch","start":"11:00","end":"16:00"}],"assignments":[{"employee_id":"e1","name":"Maria","window_key":"Mon_Lunch","day":"Mon","window":"Lunch","start":"11:00","end":"16:00","task":"Grill","hours":5,"wage":19.5,"cost":97.5}],"demand":[{"window_key":"Mon_Lunch","task":"Grill","needed":1,"assigned":1,"missing":0}],"gaps":[],"employees":[{"employee_id":"e1","name":"Maria","tasks":["Grill","Prep"],"rates":{"Grill":19.5,"Prep":19.5},"min_hours":null,"max_hours":18,"hours_scheduled":15}]}
```

Each `window` has `key`, `day`, `name`, `start`, and `end`. Each assignment has `employee_id`, `name`, `window_key`, `day`, `window`, `start`, `end`, `task`, `hours`, `wage`, and `cost`. Each demand row has `window_key`, `task`, `needed`, `assigned`, and `missing`; each gap has `gap_id`, `window_key`, `day`, `window`, `task`, `needed`, `assigned`, and `short_by`. Employee rows have `employee_id`, `name`, `tasks`, `rates`, `min_hours`, `max_hours`, and `hours_scheduled`.

`explanation` is `{ "summary": "...", "gap_explanations": [...] }`. Each gap explanation includes `gap_id`, `explanation`, `suggested_action`, and `needs_manager_approval`. In the real solver path, the summary and explanations are built in code; candidate suggestions may use `gap_candidates()`. No LLM-written schedule explanation is currently used.

## 8. Design decisions and safety

- The OpenRouter key is read by backend code from `api_key`; it is not returned to the browser.
- The backend checks maximum hours, the 40-hour threshold, workbook overtime threshold, and less-than-11-hour turnaround for covers; the LLM does not make approval decisions.
- LLM output must be JSON with allowed action, employee, day, window, and task values. The backend retries once after validation failure; API errors, timeouts, missing key, or invalid second response use the keyword parser.
- Solver output may vary. The demo is solved once at startup and cached; Reset restores that cache rather than re-solving.
- A call-out re-plan proposal is held in memory. Approve applies the stored normalized result without calling the solver again; reject discards the proposal.

## 9. Demo data and click-through

The demo workbook is [`ui/demo_data/demo_input.xlsx`](demo_data/demo_input.xlsx), generated from the root [`schedule_input_template.xlsx`](../schedule_input_template.xlsx) by [`ui/demo_data/make_demo_workbook.py`](demo_data/make_demo_workbook.py). Regenerate and run its validation/solve report from the repository root with:

```bash
python ui/demo_data/make_demo_workbook.py
```

The workbook defines five tasks: Fry Station, Grill, Expo, Register, and Floor. Only Maria Alvarez and Leo Martinez have Grill proficiency; Maria is unavailable Saturday Dinner Rush. The workbook requests two Grill staff for Saturday Dinner Rush and two Expo staff for Friday Dinner Rush, where several Expo-qualified employees are unavailable. The demo is designed to show a one-person shortfall for **Sat Dinner Rush Grill** and **Fri Dinner Rush Expo**. The generator's report checks for 2–3 solver gaps, an optimal/feasible result, no employee above their max hours, and a solve under five seconds. Those checks require the solver dependencies and an actual run.

1. Start the server and choose **Use demo data**. This displays the cached startup solve, or mock data if real initialization fell back.
2. Click a generated call-out example. It uses an employee and window from the displayed assignments; with a real cached solve, the call-out is removed and a re-plan is attempted.
3. Review the **BonApp suggests a re-plan** card, its diff and flags; choose **Approve** or **Reject**.
4. To see the premium-pay approval path, request **Maria Alvarez will cover Sat Dinner Rush Grill** when that gap exists. The banner appears only if the current hours/threshold/turnaround rules require approval; otherwise the request is rejected or applied according to the current schedule.
5. Choose **Reset demo** to restore the startup cache, then use **Data In** to return to upload.

The solver is not guaranteed deterministic, so assignments and some example chips can differ between server startups. The configured demand and availability rules above are fixed in the demo workbook.

## 10. For teammates

- **Changed solver result:** edit `ui/solver_bridge.py`, especially `normalize(result, inputs)` and, if the input structures changed, `load_workbook_input()` / `solve()`. Preserve the UI contract in Section 7 or update the UI consumers in `ui/static/index.html` and `ui/server.py` together.
- **New example message:** edit `renderExamples(schedule)` in `ui/static/index.html`. Current examples are generated from live assignments, gaps, and eligible roster members.
- **Names and fields to keep aligned:** the imported function names `load_workbook_input`, `to_scheduler_inputs`, `build_shifts`, `run_pipeline`, `gap_candidates`, and `reoptimize`; schedule keys such as `window_key`, `task`, `needed`, `missing`, and `employee_id`; and the re-plan diff entry keys `employee_id`, `employee_name`, `shift`, and `role`.
- **Run without changing teammate modules:** use the Quick start commands. The bridge imports the existing root modules and keeps translations in `/ui`.
- `ui/adapters.py` still contains mock `standardize()`, `build_schedule()`, and `explain()` hooks. They are not the real workbook pipeline; do not assume that replacing these functions connects the browser to the solver.

## 11. Known limitations

- State is in one server process's memory; it is not persisted or shared across workers.
- The app has no authentication, authorization, or tenant isolation.
- Proficiency scores are recorded by workbook input but are not used by the current scheduler to rank assignments.
- Cover requests check for a matching gap and skill, whether the employee already works that window, and approval thresholds; the current handler does not verify the employee's workbook availability for that window.
- LLM support is limited to understanding updates and answering from the schedule context. Explanations are code-generated, and the UI has no demand-forecasting or fairness-scoring feature.
